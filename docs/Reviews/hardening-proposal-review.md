# Independent review: agent security hardening proposal (T-043)

Reviewer: fresh-context Security & QA. Date: 2026-10-30. Scope: `docs/research/agent-security-hardening-proposal.md` (P), `docs/proposals/agent-hardening/{guard.py (G), test_guard.py (T), settings.proposed.json (S)}`, against `docs/prompts/milestone-1-agent-security-hardening.md` and `docs/research/s-12-agent-isolation-results.md`.
Method: read all files; ran `test_guard.py` (16 tests, 15 pass, 1 skipped, matches P line 89); ran `guard.py` by hand with crafted payloads against a temp project in the session scratchpad (nothing written into the repo). No Claude Code session was run, so nothing about how Claude Code treats the hook is verified.

Verdict: accept with changes. The four deliverables exist, the constraints are respected (nothing installed, no new headless runs, no bypass), and the operating model matches the preferred one. The labelling is mostly honest. But the guard has real gaps that contradict claims in P, and the B-04 plan leaks its own answer key. Fix the High items before the founder is asked to activate.

## Findings

### High

**H1. Read, Glob and Grep are auto-allowed on any path, including outside the project and secrets.** G lines 129-130 and 142-143: for a known role, a READ tool goes straight to an explicit `allow`; for an unknown role also. No path in `file_path`, `path` or `pattern` is checked. Confirmed by running: `security-qa` Read of `<home>/.ssh/id_rsa` -> exit 0 with allow; `market-researcher` Read `.env` -> allow; Grep with `path: C:/Users` -> allow. A hook `allow` is meant to suppress the permission prompt, so the guard converts what would be a prompt into silent access. The S deny rules `Read(.env*)` and `Read(secrets/**)` are the only cover, and their matching semantics are unverified (P line 73; and whether a hook allow beats a deny is A6, not run). This contradicts P principle 5 ("protected paths are blocked for every role") and the T1 threat (an injected research agent can read secrets and then send them out through WebFetch, which P admits).
Fix: in `decide`, run `resolve()` on every READ tool's path argument (default to root when absent), block anything outside the root or protected (`.env*`, `secrets/`, key files, `.git/`), and return `None` (no opinion) rather than `allow` for reads, so the prompt flow stays. Add tests for read of `.env`, `../outside`, an absolute outside path.

**H2. B-04 answer key is in the repository the reviewer can read.** P lines 123-132 list all seven seeded defects (D1-D7, classes, must-catch flags) inside `docs/research/`, while P line 121 says the manifest lives outside the repo "so the reviewer cannot read it". The reviewer has Read/Glob/Grep over the whole repo (and, per H1, outside it), so it can read the table, `CLAUDE.md` and this proposal. Also, run N can read reports from runs 1..N-1 in `docs/Reviews/` and the control-versus-seeded difference is visible in Git history and commit messages. The trial is invalid as designed.
Fix: remove the per-defect table from the in-repo file (describe classes only, keep the manifest and scoring key outside, with only a hash recorded), or run the trial on a copy of the repository without `docs/research/` and `docs/Reviews/`. Neutral commit messages and branch names. Give each run its own report folder the next run cannot read, or restrict reviewer reads to the trial folder through the hook (see H1 fix).

**H3. The Engineer's scope file can be made writable by the Engineer, and "too wide" scope is not rejected.** P principle 6 (line 86) says a too-wide scope blocks every Engineer write, and P line 28/T4 say the scope file is not writable by the Engineer. G `engineer_scope` (lines 72-85) only rejects absolute, `..`, `:`, protected and `docs/task-scope*` entries. A scope of `["docs/", "src/app.py"]` is accepted. Confirmed by running: with that scope the Engineer's Write to `docs/task-scope/current.json` and to `docs/Reviews/x.md` both returned allow. The Engineer can then widen its own scope, overwrite reviews, the ledger and decision records. There is no write-time rule excluding `SCOPE_FILE` for the Engineer, and the test (T line 144-146) only checks the bad-entry cases, not that the Engineer cannot write the scope file under a wide scope.
Fix: at write time, block any non-Orchestrator write to `docs/task-scope/` and `docs/Reviews/` regardless of scope; in `engineer_scope` reject entries that are a directory with fewer than two path segments, any entry under `docs/` other than a named subfolder, and the root; add tests for each. Also note the Orchestrator can write the scope file (G line 22), so author and approver of the Engineer's scope are the same model; say that the founder approves the scope file before use.

### Medium

**M1. "Fail-closed" is overstated for hook failure.** P line 83 and T5 (line 55) assume a missing or crashing hook "produces no allow, so permission prompts or `dontAsk` apply". That is fail-to-prompt, not fail-closed: in `default` mode (S line 4) a missing Python, a Windows Store `python` stub, or any non-2 exit is a non-blocking error and the call proceeds to normal permission handling, where S allows Read/Glob/Grep and several Git commands unprompted and the founder may click "yes" on writes. The guard itself is genuinely default-deny; the surrounding system is not shown to be. P admits it is unverified, but the section title, the summary and the design name still say "fail-closed".
Fix: reword to "default-deny script; fail-to-prompt on hook failure (unverified)", or add a second layer that denies without the hook (for example per-role `permissions.deny` in the agent definitions is not available, so use `dontAsk` for subagent sessions). Make A3-A5 gating, as P already says, and add "hook wiped by a failing interpreter path" to the Windows check (`python` vs `py`).

**M2. Subagent identification fails open.** G lines 115-123: a payload without `agent_type` (or an empty one) is treated as the founder-supervised main session and gets "no opinion" (confirmed: `{"tool_name":"Write","agent_id":"abc",...}` -> exit 0, no block, and `mcp__x__send` from the main session -> exit 0). S-12 E8 observed `agent_id` plus `agent_type` for a subagent; nothing shows `agent_type` is always present (forks, other builds, `--agent` main sessions). P line 91 records field names as assumed. A payload with `agent_id` but no `agent_type` should be blocked.
Fix: if `agent_id` is present and `agent_type` is missing or empty, exit 2. Add a test. Also state in P section 2.1 that the main session has no connector (mcp) control at all from this guard (T7 mitigation covers subagents only).

**M3. Shell allow-list gaps, and the allow decision removes the prompt.** The Engineer's shell inside the container gets an explicit `allow` for anything that avoids a few regexes. Confirmed with `EVENTS_DEV_CONTAINER=1`: `git -C . push origin HEAD:main`, `git switch main`, `git branch -D x`, `find . -delete`, `python -c "import urllib.request"` and `Remove-Item -Recurse x` all return allow (G line 38 only matches `git push` with no global options, `rm -r*`, curl, wget). The Orchestrator's read-only regex (G line 35) accepts `git diff --no-index ~/.ssh/id_rsa /dev/null` (confirmed allow), which reads arbitrary host files; `~` and absolute paths are in the permitted character set. `$` in the regex also matches before a trailing newline (`git status\n` allowed; harmless but sloppy). P presents the Bash guard as a "mistake guard, not a boundary", which is fair, but the setting that makes it an auto-allow rather than "no opinion + prompt" is a choice that widens the risk.
Fix: for the Engineer return no-opinion (let prompts or the container's own limits apply) instead of an allow; add `-C`, `-c`, `--git-dir`, `--work-tree`, `switch`, `branch -D`, `update-ref`, `rebase`, `reset` to the never-list, or better invert it to an allow-list of test commands; for the Orchestrator add `--no-index`, reject any argument containing `~`, `..`, or a leading `/`, and use `re.fullmatch`.

**M4. Settings deny rule for pushes to `main` misses common forms.** S line 27 `Bash(git push * main*)` needs a space before `main`. `git push origin HEAD:main`, `git push origin +main`, `git push origin HEAD:refs/heads/main` and a bare `git push` on `main` do not match, and `git -C . push` bypasses all push rules in S lines 25-27. The main session relies on these (the hook has no opinion there). P T10 lists these denies as unverified and that is accurate, but the specific known gaps are not stated, and CLAUDE.md section 5 makes this the key rule.
Fix: deny `Bash(git push*)` and `Bash(git * push*)` outright for non-task branches or deny all pushes and rely on the founder-run push; add `Bash(git -C*)`. Also note the Windows `PowerShell` tool exists in this environment: S has no `PowerShell(...)` deny or allow rules, so `Remove-Item`, `Invoke-WebRequest` and git via PowerShell are covered only by prompts in the main session.

**M5. Protected path list is too short.** G lines 30-32, S deny list. Not protected: `.mcp.json`, `.vscode/` (tasks that auto-run), `.github/` (CI), `.gitmodules`, `.gitattributes`, `CLAUDE.local.md`, `.npmrc`, `package.json` scripts and similar command-execution entry points, `.git` as a file (worktree pointer, `r == ".git"` is not matched by `startswith(".git/")`). The Engineer can write any of these if its scope names them (the scope check only excludes the protected list, G line 82). `.vscode/tasks.json` was blocked in my test only because it was not in scope.
Fix: add these to PROTECTED and to the S deny list; treat `.git` exact. Tests for each.

**M6. B-04 statistics and adjudication do not support the stated hypothesis.** P line 114 hypothesis says the reviewer "catches the must-catch defects reliably". Three runs and a 2-of-3 threshold cannot show reliability: a reviewer with a true 50% detection rate per defect passes each defect half the time; with 70% it passes all four must-catch defects only about 38% of the time. P line 149 does say "feasibility, not a reliability rate", but the hypothesis wording and the pass thresholds should match. The "High or Medium false positive" criterion (line 146) has no pre-written rule for what counts as a false positive: the control change is LLM-written synthetic code, so a reviewer may find genuine unseeded defects. Severity is rated by the scorer after seeing the report. "Reports state what they could not check" is not measurable.
Fix: restate the question as feasibility; pre-register a scoring rubric (detected = report cites the file plus the class; any finding not in the manifest is reviewed against the control code before being called a false positive; severity rated blind to run identity by a second rater or the founder); fix the control-code defects before the trial by having the author pass a static review; define "states limits" as a non-empty section.

**M7. B-04 is not reproducible as written, and its dependencies are out of order.** Materials "none exist yet" (P line 118); the module, tests, prompt template text, defect patches and scoring sheet are not specified at code level, so a third party cannot rerun. Run order is unclear: the trial must run under activated settings and hooks, yet P line 116 uses the `security-qa` definition "with the project definition", which today still has `Bash` (`.claude/agents/security-qa.md` line 4: `tools: Read, Glob, Grep, Write, Bash`) because the removal is "not applied" (P line 31). Decision 4 does not state that decisions 1 and 3 and checks A1-A4 must come first. The procedure also needs hashes and a diff (steps 1, 3) but the Orchestrator allow-list has no `git hash-object` / `ls-files -s`, and nobody is named as the party that makes the seeded commit (the Orchestrator cannot write `spikes/`; the Engineer needs the scope file). Parties are all the same model, which P acknowledges.
Fix: commit the base module, task text, prompt template and a script that applies each seeded patch (answer key kept outside, hash recorded); add an explicit ordering (decision 1 applied, activation A1-A10 passed, then B-04); name the committer (founder-supervised main session); add `git hash-object` and `git ls-files -s` to the Orchestrator list or have the main session do the hashing; record Claude Code version, model and temperature-equivalent settings per run.

### Low

**L1. Usability: relative paths beginning `./` are blocked** (G line 48 regex catches `./` because `.` is followed by `/`). Confirmed: `./docs/research/a.md` -> exit 2. Claude Code normally passes absolute paths, so likely harmless, but P principle 4 says it rejects "`..` or `./` segments" without stating the side effect on legitimate paths; filenames containing `~<digit>` are also rejected (G line 55). Note, or tighten the regex to dot-segments.

**L2. Agent tool name.** G allows `Agent` for the Orchestrator, T line 93 blocks `Task` for the Engineer. If the tool is reported as `Task` in the hook payload on a given version, delegation is blocked (fail-closed, safe, but breaks the workflow). Add A-check: confirm the tool name seen by the hook for delegation.

**L3. `under()` lower-cases on all platforms** (G lines 60-63), so on Linux `docs/reviews/x` matches `docs/Reviews/`. Harmless now (Windows-only), note for the Linux/container case, where the Engineer's container is probably Linux.

**L4. Test quality.** The tests are mostly behavioural and several would catch real regressions (path tricks, garbage input, role-name exactness, scope file corruption, the trailing-dot case that exposed a real gap). Weaknesses: no test for Read paths (H1), `agent_id` without `agent_type` (M2), wide scope (H3), `--no-index` or `-C` (M3); `test_main_session_protected_only` asserts exit 0 for any main-session Bash, which cements the no-opinion behaviour as intended; the `allowed` helper only string-matches `"permissionDecision": "allow"` (fine, but no test that the output is valid JSON with the right hook schema); the Engineer shell test asserts only exit codes (`test_engineer_shell_needs_dev_env` line 158 would pass on exit 0 with no allow decision); no test for tool_input being a non-dict. Symlink escape is skipped on this machine, so the claim that symlinks are resolved rests on reading `realpath` only.

**L5. Minor inconsistencies and claim wording.**
- P line 89 says "Python 3.x" with no version; the guard says 3.8+. Record the version.
- P line 51 (T1) cites "no shell for those roles ... observed in S-12 (E1)": E1 was one run on one agent; "tool-list control, one run" is the accurate label.
- P line 54 (T4): "Deny rule held even under bypass (E4a, E4e)" is accurate for Write on a folder, but S relies on `Write(.claude/**)` and `Edit(CLAUDE.md)` forms never observed; the "observed" shapes in P line 73 are `Write(folder/**)`, `Edit(folder/**)`, `Bash(rm *)` only, which is stated correctly. Keep.
- P line 35 states unknown roles like `Explore` "may only Read, Glob and Grep", and G allows them through with an `allow`: also see H1.
- S line 4 `disableBypassPermissionsMode` and the hook command form on Windows are correctly flagged as source claims. The `python` binary name on Windows may differ (`py`, Store stub); add to A4.
- P section 1 summary says "Writes by every role are confined"; true only for Write/Edit/MultiEdit/NotebookEdit through the guard, not for Bash by the Engineer (documented in the next sentence; tighten the first).

## Checklist against the founder's asks

1. Proposed settings: present (S plus P section 4); not installed. Pass, subject to M4 and M5.
2. Fail-closed hook design: present; guard is default-deny but the system-level "fail closed" claim is unproven (M1) and has real gaps (H1, H3, M2, M3).
3. Concise threat model: present, 12 threats, labelled; concise enough. Missing threats: read-of-secrets (H1) and scope-self-widening (H3).
4. Reproducible B-04 plan: criteria set before running, which is good; not reproducible and not independent as written (H2, M6, M7).
Constraints: no extra headless runs, no paid API, no bypass, nothing installed at `.claude/settings.json`, real guest data not involved: all respected. The S-12 distinction (a hook restricts Write/Edit, a shell is not contained) is respected and not overclaimed.
Operating model: matches the preferred model on paper (no shell for research, review; Engineer shell only in a controlled environment, Orchestrator read-only Git). The controlled environment is undesigned, which P states.

## What I could not check

- The exact hook payload fields beyond `agent_type`, `tool_name`, and `file_path` for Write/Edit, including Read/Glob/Grep argument names, `agent_id` presence, and the tool name used for delegation.
- Deny-rule pattern semantics (`.env*` anchoring, cwd-relative vs project-relative, `//` forms) and `disableBypassPermissionsMode`.
- Symlink behaviour (test skipped here), Linux/macOS behaviour, Windows reserved device names, hardlinks, and time-of-check/time-of-use races.
- Whether `git diff` option abbreviations can bypass the `--output` block: I tried `--outp` and `--out` on the local Git and both were rejected as invalid options, so no bypass was found on this version.
- Anything about the Engineer container, since it is not designed.
- The accuracy of source-claimed Claude Code documentation; no network was used.
